# Plan: Refactor to Database-backed Job Queue with Docker Compose

## 1. Database Schema Update
- Add a new table `jobsTable` in `src/db/schema.ts` to store incoming user requests.
- Fields: `id`, `chatId`, `messageId`, `text`, `media` (JSON), `status` (pending, processing, completed, error), `errorLog`, `createdAt`, `updatedAt`.
- This ensures all incoming messages are persisted immediately.

## 2. Decouple Telegram Bot (`src/bot.ts`)
- Remove the in-memory `activeProcessing` lock.
- Update message handlers: Instead of calling `runAutomatedPipeline` directly, insert the extracted `text` and `media` into `jobsTable` with status `pending`.
- Reply to the user with an acknowledgement (e.g., "⏳ Pesan diterima dan masuk antrean (Antrean ke-X).").

## 3. Background Worker (`src/worker.ts`)
- Create a new worker process file `src/worker.ts`.
- Implement a polling loop (or use Postgres LISTEN/NOTIFY if appropriate, but simple polling is robust) that looks for `pending` jobs.
- When a job is picked up, mark it as `processing`.
- Call the refactored `runAutomatedPipeline`.
- Upon success, mark as `completed`. On failure, mark as `error` and save the `errorLog`.
- Implement a graceful shutdown for the worker so it finishes the current job before exiting.

## 4. Refactor Pipeline (`src/agent.ts`)
- Modify `runAutomatedPipeline` to accept raw parameters (`chatId`, `messageId`, `text`, `media`, and a `Telegram` instance) instead of the full Telegraf `ctx`.
- Update the way status messages ("🔍 Mencari informasi...", etc.) are sent and edited, since we won't have the standard `ctx` inside the worker, but we can use `telegram.sendMessage` and `telegram.editMessageText`.

## 5. Docker Compose & Resilience
- Create `docker-compose.yml` with two services (both connecting to the external DB via `.env`):
  - `bot`: Runs the Telegram Bot and Express API.
  - `worker`: Runs the background job processor (`worker.ts`).
- Update `package.json` scripts to have `start:bot`, `start:worker`, and `db:push`.
- By separating the bot and worker into different containers, if the AI processing crashes or runs out of memory, the bot will remain online and continue accepting new queue inputs, fulfilling the user's requirement for resilience.
